# 网链资源需求匹配

## 1. 适用范围

`NRM_RESOURCE_DEMAND_V1`是v0.10第一阶段用于开发、测试和内部预验收的严格文本格式，
对应公共schema `nrm.resource_demand.v1`。它不是甲方正式需求格式，不包含隐含业务门限、
自动资源分配、自动网络控制或优化算法。

甲方格式只能通过后续适配层转换为相同公共值对象。正式格式和候选资源没有提供时，不得
从文件名、业务名称或自由文本推导字段和候选值。

### 可直接加载的合同验收样例

`data/resource_demands/contract_acceptance_37node-r1.demand`包含12项需求，覆盖Link-11、
Link-16、卫通和CDL，并与`data/network_plans/contract_acceptance_37node-r1.nrm`中的需求
逐项对应。进入Warlock“需求匹配”页点击“加载”即可传入；该文件不会自动修改通信资源。

页面明细采用“业务需求、匹配结果、约束差距、调整建议、技术依据”五个二级页签，每次只显示一张
全高表。加载后显示业务需求；执行匹配成功且无失败项时进入匹配结果；存在失败项时优先显示
调整建议，没有可用建议时显示约束差距。“调整建议”按通信任务聚合，一项任务只显示一行中文结论、建议资源、
建议路由和原因；候选对象ID、排序、来源/置信度和原始证据单独保留在“技术依据”。各页仍支持水平、垂直滚动和拖动列宽。

AFSIM实时快照更新后，原匹配结果不再属于“当前有效结果”，但界面会保留上一轮匹配明细供录像和
对比。顶部状态明确标注“上一轮匹配结果已过期”、当前快照版本和结果快照版本；需要当前结论时再次
点击“执行匹配”。加载新需求集、修订需求或卸载需求会清除该历史，避免跨需求集混用。

## 2. 词法规则

- 文件使用UTF-8或ASCII文本，每条记录占一行；
- 空行和首个非空白字符为`#`的整行注释可忽略；
- 所有字符串使用`std::quoted`兼容的双引号形式；
- 枚举、整数、浮点数和布尔值不得加引号；
- 布尔值只能是`0`或`1`；
- 所有浮点数必须有限，不接受`NaN`、`Inf`或`-Inf`；
- 每行规定字段后不得存在尾随token；
- 未知magic、记录类型、枚举值或悬空引用拒绝整个文件。

## 3. 完整文法

首个非注释记录必须是头记录：

```text
NRM_RESOURCE_DEMAND_V1 "demandSetId" revision "configVersion" "providerId" "createdTimeUtc" ORIGIN CONFIDENCE valid "previousDemandSetId" previousRevision
```

其中：

- `revision`必须大于0，`previousRevision`为无符号整数；
- `ORIGIN`为`AFSIM_INTERNAL`、`CUSTOMER_MODULE`、`REPLAY`、
  `PARAMETERIZED_MODEL`、`ESTIMATED`或`DERIVED`；
- `CONFIDENCE`为`LOW`、`MEDIUM`或`HIGH`；
- 无前一修订时，前一需求集ID为空字符串且前一修订为0。

头记录后允许：

```text
DEMAND "demandId" "missionStage" "businessType" "sourcePlatform" "destinationPlatform" payloadBits businessTrafficBps requiredBandwidthBps maximumDelayMs minimumPdrPercent maximumDistanceM minimumNetworkSize

DEMAND_NETWORK "demandId" NETWORK_TYPE
```

`NETWORK_TYPE`为`LINK11`、`LINK16`、`SATCOM`或`CDL`。一条需求可有零至多条
`DEMAND_NETWORK`记录；零条表示未限定网络类型，不表示可以使用`UNKNOWN`。

## 4. 字段与约束

- `demandId`在需求集内唯一；
- 需求集ID、需求ID、任务阶段、业务类型、源平台和目的平台不得为空；
- 源平台和目的平台不得相同；
- payload为无符号整数，其他数值不得为负；
- PDR必须位于0至100；
- 数值0表示调用方未设置对应硬约束；
- `businessTrafficBps`和`requiredBandwidthBps`都保留，能力请求使用二者较大值；
- 不从`missionStage`或`businessType`推导任何数值门限。

解析成功只证明内部语法成立。端点、快照、profile、业务支持和能力数据由匹配服务校验。

## 5. Repository语义

- 加载失败不覆盖当前有效需求集；
- 当前活动的同一`demandSetId + revision`拒绝重复加载；
- 显式卸载后允许重新加载同一文件；
- 编辑创建递增revision的新草案，旧匹配结果失效；
- 保存使用目标目录临时文件、flush和原子rename；
- 目标文件已存在时拒绝覆盖；
- 显式路径为空时可使用`NRM_DEMAND_STORE_DIR`；
- 保存后重新加载必须保持值对象语义等价。

## 6. 匹配口径

检查顺序固定为：

```text
PATH, NETWORK_SIZE, DISTANCE, BANDWIDTH, TRAFFIC, DELAY, PDR, BUSINESS_TYPE
```

PATH和BUSINESS_TYPE始终适用，其他检查仅在需求值大于0时适用。带宽与业务流量分别输出
检查，但都使用同一`CapabilityResult.transmissionRateBps`。每条有效需求只调用一次
`CommunicationCapabilityService::Query`。

- PATH只依据能力请求有效性和路径可用性；未启用约束的指标缺失不污染PATH结论；
- NETWORK_SIZE按允许网络中的在线平台名去重计数，同一平台加入多网时只计一次；
- 能力路径包含多种网络类型时，BUSINESS_TYPE必须在路径经过的每种网络类型上得到profile支持。

裕量方向固定：

- 下限约束：`当前可用值 - 需求值`；
- 上限约束：`允许上限 - 当前实际值`；
- PATH和BUSINESS_TYPE：通过为0，不通过为-1；
- 正数或0表示满足，负数表示不满足；
- 必需数据无效时current和margin保持`valid=false`，不得写0冒充观测值。

任一适用检查数据无效则整体为`DATA_INVALID`；数据有效但任一检查失败为
`UNSATISFIED`；全部适用检查通过为`SATISFIED`。

需求来源明确写为`PARAMETERIZED_MODEL`时，允许在当前AFSIM统计窗口尚无样本的情况下，
使用版本化network profile中的容量、候选PDR和建链时延进行低置信度近似。来源为
`AFSIM_INTERNAL`或`CUSTOMER_MODULE`时不启用该回退，缺失实测指标仍输出`DATA_INVALID`。

## 7. 规划证据

同时提供规划和规划推演结果时，必须一致匹配：

- planId；
- revision；
- 由规划完整内容计算的planFingerprint；
- 推演snapshotVersion与当前snapshotVersion。

任何一项不一致时拒绝拼接规划证据并输出固定原因码。只有规划而没有推演结果时可记录规划
身份和生成有限候选建议，但不把不存在的推演结果当作能力证据。

## 8. 六类建议

建议顺序固定为`FREQUENCY`、`STATION`、`CHANNEL`、`SUBNET`、`TIMESLOT`、
`ROUTE`，每类恰好输出一条`AVAILABLE`或`UNAVAILABLE`结果。

- 调用方显式候选集优先；没有候选集但已经加载规划时，频率、信道、子网和时隙可使用
  规划allocation中明确给出的值，并固定标记`LOW`置信度和`LOADED_PLAN`证据；
- 频率候选还必须能在所引用规划allocation/profile中验证；
- 站点候选使用调用方提供的路径可行性、匹配状态和最小裕量证据，不执行第二次路径搜索；
- 信道和时隙仅排除显式`occupied=true`候选；
- 子网必须显式支持业务类型且成员容量未超限；
- 路由只复用本次能力结果中的已选route；
- 相同优先级最终按候选ID排序，结果可复现；
- 规划与候选都缺少、证据无效或甲方规则缺失时不生成占位值。

所有建议都是只读分析结果，不修改规划、快照、AFSIM网络或候选输入。

需求文件加载、草案校验或修订保存失败时，Warlock集成层将固定原因码、字段和
`ResourceDemand`组件标识写入当前run的`error.log`。
